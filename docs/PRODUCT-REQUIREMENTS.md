# 产品硬约束与验收契约

状态：实施要求，非验收通过声明。以下要求约束客户端、控制台、Collector、API、策略、通知、发布和运维文档。功能必须有对应版本及测试证据；既有注释、默认开关、静态列表和预留接口不代表要求已实现。

## R1：分布式与长期容量

长期目标为 30,000 个终端客户端、站库分离、服务热备冗余，消除声明故障模型内的单点。近期版本逐项登记仍存在的单点；不能将单机试点写成高可用部署。

设计必须覆盖入口/LB、应用、Collector、数据库、后台任务、消息投递、策略签名和工件分发。应用可横向扩展，状态和任务账本外置，使用持久租约及 fencing 防止失效工作进程继续执行。多副本之间共享幂等键，不能依靠进程内 Set 或单实例 timer 防重。

数据库独立部署，主备切换需避免双主；备份恢复与热备分别演练。采用增量/心跳上报、背压、分批补报及冷热分层；不能只按平均请求数推断容量。组件选择和新增依赖在实现时完成准入。

长期验收目标：单个应用或数据库节点失效后，服务在 30 秒内恢复；对已确认提交的数据，RPO=0 必须用复制配置及故障演练证明。测试还包含网络分区、后台工作进程切换、滚动升级、签名/分发故障及恢复。30,000 个合成终端持续 24 小时，并测试集中重连和离线补报，记录报告大小、工具/资产分布、P95/P99、积压、重复和实际丢失。容量测试与高可用测试分别验收，不能互相替代。

## R2：完整 API 与模块化接入

系统每项业务能力均需可调用接口，覆盖控制台、Collector、设备接入、资产目录、检测、例外、策略、终端任务、执行回执、纠偏、通知、审计、健康和发布。维护完整清单，明确 `implemented` / `reserved`，并进行路由与契约的双向覆盖测试。

OpenAPI 契约必须定义请求/响应 Schema、参数、错误码、分页、幂等键、限流、版本兼容、异步任务与权限范围。服务间接入使用独立服务身份和最小权限；身份、租户、项目及设备范围由服务端校验，不能共享管理员浏览器会话。Webhook 需验证签名、去重、防重放并支持失败重试。

验收：独立模拟宿主完成“提交事件—读取决策—领取任务—提交回执—查询复测结果”闭环；越权、重复、超时和版本不兼容均有负向测试。预留接口返回明确 501，不返回虚构成功；仅有路径表不能视为完整对接能力。

## R3：阻断与全自动纠偏

恶意 Skill 必须在可验证的加载/执行边界禁止，MCP 必须在可验证的连接/进程启动边界拒绝；重启或重写配置后仍需有效。Skill/MCP 治理检测独立于代码质量扫描开关。每个支持的工具、系统、架构和版本记录实际控制点，明确既有连接是否受控；不能把修改配置等同于连接已拒绝。

代码质量问题进入统一闭环：

```text
发现 → 相关用户与 Agent 定向通知 → Agent 接单 → 生成并应用修复
    → 相同规则复测及必要回归 → 结果通知 → verified / failed / needs_attention
```

消息送达、接单、修改、复测通过分别记录。只有实际复测通过才可关闭，不能将通知或策略发布成功写成纠偏完成。支持人工例外及撤销；自动重试有次数、时间和影响范围上限。修复依据结构化规则与约束，项目内容和报告不得变成任意系统命令。不可逆操作、账号封禁及受保护分支继续遵守安全边界。

验收覆盖恶意与良性样本、离线、拒收、超时、错误回执、失败修复、重复任务、并发编辑、修复循环及恢复。用户通知和 Agent 任务都必须有接收确认；缺少某工具执行适配器时标明未支持，不能降格为“发了通用 Webhook 即完成”。

## R4：内置与内置市场预置允许，封禁优先

支持范围包含主流 AI Agent 内置 Skill/MCP 及内置市场内容，包括 WorkBuddy 专家团/技能和 Codex 内置能力。已核验的对应资产全量预置入库为允许，安装及升级需幂等补齐；不能依赖用户逐项手工点击录入。

目录身份至少记录工具、渠道/市场、发布者、包标识、版本及来源证据；可获得时校验签名和内容摘要。维护目录采集时间、版本与覆盖差距。名称相同不足以证明资产属于允许目录；市场新增项要通过可验证的目录同步补齐，不能以名称通配放行冒充“全量”。

同一作用域内，统一执行优先级：**命中的封禁规则 > 人工允许 > 已核验来源的预置允许 > 默认处置**。自定义封禁优先于任何预置白名单；目录刷新不得撤销已有封禁。预置允许不能被误认为人工忽略新恶意行为的决定。

服务端、策略编译、客户端执行及告警过滤均使用同一决策语义。测试精确/目录规则冲突、旧允许快照、同名冒充、内容变更、升级、目录刷新及离线缓存。规则匹配成立后，不能因加白而隐藏仍应处置的封禁事件。

## R5：按问题身份持久抑制重复告警

资产准入、发现例外和事件去重为三个独立概念。人工增加的 Skill、MCP 和代码规则允许决定必须持久化并供所有消费入口读取。

默认“同一问题”身份为：**租户/项目等适用范围 + 规则/分类 + 可信资产身份 + 实际片段指纹 + 规范化算法版本**。事件 ID、时间戳、行号不进入身份。片段指纹在端点计算，服务端不保存原始代码片段；带秘密的材料须在端点按分级处理，不能把原始代码交给通知或 LLM。

同分类、同片段换事件 ID/行号、重启或切换服务实例仍不重复告警。不同分类、不同实质片段、范围或可信资产变化、新封禁规则必须重新评估。路径白名单属于范围例外，不能宣称它实现了片段级去重；规范化不得把不同语义片段折叠成同一个允许项。

发现列表、通知、工单和纠偏任务均应用相同例外决策；保留命中计数、审计、原因、创建人及撤销入口。撤销后下一次实际命中可重新告警，历史记录不篡改。跨租户/项目误抑制、指纹缺失、算法升级、规则冲突与存储故障均需负向测试；身份不充分时不得扩大抑制范围。

## R6：4A 按产品版本分阶段交付

当前开源版不强制接入 4A，保留现有认证、身份映射、授权、吊销和审计适配接口，不继续扩展 4A 功能。未配置 4A 时，本地认证及角色权限应可独立运行；本期不因尚未对接企业 4A 而判定产品验收失败。现有企业部署验收工具不能直接作为开源版的必选验收清单。

未来企业版仍须完成企业 4A 对接，作为企业交付要求保留在路线图中，不能将“当前不强制”解释为取消企业对接。企业阶段按目标环境验证身份映射、授权边界、会话吊销及审计联动；配置故障不能静默放行。模块化服务身份 API 继续建设，独立于本期暂停的 4A 功能扩展，也不免除服务端授权。

## 安全设计检查

| 检查项 | 设计决定及当前验收状态 |
| --- | --- |
| 访问控制矩阵 | 管理员：管理目录/策略/例外；运营员：范围内处置；审计员：范围内只读；终端：仅自身报告、任务和回执；宿主服务：仅显式授权 API scope。具体拒绝项须逐接口测试，未验收 |
| 调用者声明 | Collector 接受已认证终端；纠偏调度接受管理员/受权调度器；执行器仅接受绑定设备与任务的已认证调度；所有人工触发保留操作人。适配器逐项声明允许/拒绝调用方，未验收 |
| 不可逆动作 | 账号封禁不得自动执行；生产部署和发布依据有效授权，仍通过测试、评审和回滚门禁；自动修复不得越过分支保护 |
| 匿名访问 | 仅必要登录入口及可公开工件/公钥/受限健康信息；业务数据和控制动作不得匿名访问，路由清单待全量复核 |
| 数据分级 | 合成测试资料为开发数据；真实设备软件列表、账号关联与网络标识按机密/个人信息管理；绝密和敏感个人信息不进入 LLM、事件或日志 |
| 个人信息与对外共享 | 不推定隐私委员会或数据所有者审批已完成；新增真实数据采集/共享在获得相应评审前不启用，当前开发使用合成样本 |
| 脱敏和日志 | 不记录原始片段、明文身份、秘密或完整 LLM 输入输出；仅最小摘要、等级、任务/Agent ID、时间和状态；服务端二次校验 |
| 保留期 | 安全操作审计目标 180 天；原始报告和个人信息单独最小化并按批准策略保留，不能用审计期限推导原始资料全量保留 |
| 依赖 | 当前变更不新增依赖；已有依赖继续扫描，新增组件逐项准入、精确锁定版本、审核许可证和漏洞，不推定全仓已合规 |
| 注入与输出 | 外部输入不拼入系统指令；规则与任务使用 Schema、权限及值域校验；禁止将内容直接作为脚本/SQL/HTML 执行 |
| 置信度门禁 | 自动阻断需确定性规则或符合策略的高置信决策；概率判定自动阻断阈值 >0.9，通知阈值 >0.75；低置信与高风险动作按既有基线处理，不把严重等级冒充置信度 |
| 权限组合 | 采集、判定、通知、执行采用独立职责和身份；禁止同一 Agent 读取机密后任意外发，禁止无审计修改或自批任务 |
| 漏洞覆盖 | V01–V12 均适用于相关 API、解析、认证、数据、依赖及可选 LLM 修复路径；逐能力建立负向测试，不因需求文档存在即打通过勾 |

## 实施顺序与证据

1. 统一封禁优先级、可信资产身份及持久发现指纹，修正各入口的抑制和通知语义。
2. 完成治理检测、真实阻断、定向通知、Agent 纠偏和复测回执。
3. 补齐 API 数据契约和服务身份；用独立模拟宿主验收模块化接入。当前开源版按不依赖 4A 的范围验收，不新增 4A 功能；企业 4A 对接留待企业阶段实施。
4. 外置任务与幂等状态，推进 Collector 共享存储、站库分离和热备，再分别验收容量与高可用。

各阶段持续保留客户端可信更新、安装卸载与恢复门禁。[标签存储验证](LABEL-STORAGE.md)描述已实现的局部行为；[高可用设计](HA-ARCHITECTURE.md)属于长期设计。本文不宣称其中任一端到端目标已完成。
